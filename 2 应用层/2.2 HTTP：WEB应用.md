## 2.2.1 WEB简单回顾

WEB采用C/S模式，客户机发出请求，服务器为客户机提供服务。

Web页面由一系列对象组成，包括HTML文件、图片、音视频文件、JS等等。任何一个对象都可以用URL定位，如：127.0.0.1/web/index.html

URL是一种虚拟路径。例如，对于上面的例子127.0.0.1/web/index.html（计网第一次实验），我的文件实际上存储在服务器的F:/learningapp/....../web/index.html中（物理目录）。由虚拟路径到物理路径的映射由WEB服务器维护。

WEB内容的传输通过传输层的TCP协议。首先客户端启动到服务器的连接（服务器端口一般为80），服务器接受连接，HTTP报文在两进程间进行交换，完成后关闭连接。

此外http是无状态的，服务器不会保留任何访问过的请求信息。

## 2.2.2 HTTP报文
### 请求报文

请求报文的典型格式：
```json
GET /index.html HTTP/1.1\r\n    // 请求行
Host: www-net.cs.umass.edu\r\n  // 服务器地址
User-Agent: FireFox/3.6.10\r\n  // 客户端机器类型
Accept: text/html,application/xhtml+xml\r\n // 可接受的文件类型
Accept-Language: en-us,en;q=0.5\r\n
Accept-Encoding: gzip,deflate\r\n
Accept-Charset: ISO-8859-1,utf-8;q=0.7\r\n
Keep-Alive: 115\r\n             // 持久连接时间
Connection: keep-alive\r\n      // 持久连接
```

请求行支持的方法包括：
- GET：向服务器请求指定URL的对象
- POST：向服务器提交表单数据，也可以同时请求一个WEB页面
- HEAD：返回响应报文，不包含请求的对象
- PUT：上传的文件放在实体主体字段中，目标路径由URL标明
- DELETE：删除URL指定的文件

此外，上传表单数据也可以通过URL的方式，例如豆瓣里`music.douban.com/pop?start=20`，`?`后的就是表单数据，网页使用它来实现翻页。

但这种方法上传的数据是明文，安全性低，不适合传输隐私数据。

### 响应报文

响应报文的典型格式：
```json
HTTP/1.1 200 OK\r\n                    // 状态行，包含状态码、状态短语
Date: Tue, 8 Oct 2024 17:20:55 GMT\r\n // 请求日期
Server: Apache/2.0.52(CentOS)\r\n      // 服务器类型
Last-Modified: Tue, 30 Oct 2007 17:00:02 GMT\r\n // 最后更新时间
Accept-Ranges: bytes\r\n
Content-Length: 2652\r\n               // 内容长度
Keep-Alive: timeout=10, max=100\r\n
Connection: Keep-Alive\r\n
Content-Type: text/html; charset=ISO-8859-1\r\n
```

常见响应状态码：
- 200 OK：请求成功，请求对象在报文中😋
- 301 Moved Permanently：被请求的对象被移动过，新的位置在报文中有说明😦
- 400 Bad Request：服务器不懂你的请求报文😡
- 404 Not Found：找不到请求的对象🧐
- 505 HTTP Version Not Supported：服务器不支持请求报文使用的HTTP协议版本🤡

## 2.2.3 HTTP协议的更新

HTTP/1.0采用非持久连接，传输过程可一般性的描述为：
1. 客户端请求连接，0.5RTT
2. 服务器收到请求建立连接，0.5RTT
3. 客户端请求对象，0.5RTT
4. 服务器收到请求，传输对象，0.5RTT+文件传输时间
5. 发送完毕后，服务器关闭连接

传输一个对象的总时间为：$2RTT+文件传输时间$。

HTTP/1.1更新了持久连接，即服务器发送响应后，不断开连接（上面的步骤5），而是保持连接，直到休息足够长时间后才断开连接。

持久连接又分为非流水线方式和流水线方式。非流水线方式：一个对象传输完成后再传输下一个；流水线方式：一次性发送所有请求，慢慢接收。

HTTP/1.1改善了上一版本中传输时连接时间过长的问题，但仍有缺陷：存在多个对象时，小对象会被排在前面的大对象阻塞。

HTTP/2采用了报文分帧的方式解决这一问题。将所有对象按一定的大小等分成若干份，按序传输每帧。例如对象$O_1,O_2,O_3,O_4$，HTTP/1.1中，若$O_1$较大，需等到$O_1$传输完成，后面的小对象才能开始传输。但在HTTP/2中，会将报文分帧，例如$O_1$分9帧，$O_2,O_3$分1帧，$O_4$分两帧，则传输顺序为：$O_{11},O_{21},O_{31},O_{41},O_{12},O_{42},O_{13},...,O_{49}$。这样小对象也能在初始时完成传输。

HTTP/2减少了对象访问的<font color=red>感知时延</font>。

HTTP/3甚至将传输层协议从TDP改为了UDP，然后将可靠数据传输在应用层实现，设计了QUIC协议，将HTTP改装为HTTP over QUIC，得到了HTTP/3。
