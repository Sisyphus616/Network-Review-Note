不可靠信道的特性决定了可靠数据传输协议（rdt）的复杂性。

## 3.2.1 可靠数据传输模型

可以建立一个模型描述可靠数据传输：
```plaintext
	|                                       ^
	V                                       |
rdt_send()                            deliver_data()
	|                                       |
-----------                             ----------
|  发送方  |                             |  接收方 |
-----------                             ----------
	|                                       |
udt_send()                               rdt_rcv()
	|                                       |
	-----不可靠信道------>--------------------
```

其中rdt是可靠数据传输，udt是不可靠数据传输（经过不可靠信道）。rdt_send()由上层调用，udt_send()由rdt调用，rdt_rcv()由下层调用，deliver_data()由接收方rdt调用。

可以使用有限状态机分别表述发送方和接收方。

## 3.2.2 可靠数据传输的原理

### rdt1.0

rdt1.0的条件为底层信道完全可靠，既不会产生比特错误，也不会丢包。

如果用有限状态机描述，接收方和发送方都可以用一个状态表示。
- 发送方：只要上层来了数据就发
- 接收方：只要下层接收到数据就递交到上层

rdt1.0的策略就是，把不可靠数据当可靠的处理。

### rdt2.0

rdt2.0在1.0的基础上，允许信道可能出现比特差错，但分组仍然是按序到达不丢失的。

这里采取的策略为接收方主导，即当接收方收到错误分组时，发送NAK确认，发送方收到出错确认后进行重传。

- 发送方：两个状态
	1. 等待上层调用：若收到上层数据，则打包数据和校验和，发送，进入状态2；
	2. 等待确认：收到NAK则重发，状态不变；收到ACK则进入状态1。
- 接收方：收到错误分组则发送NAK，否则递交数据并发送ACK。

### rdt2.1

rdt2.0有一个致命错误，即没有考虑ACK/NAK受损的情况。此外，重传会导致出现大量重复分组，接收方无法判断接收的是重发的还是新的分组。

对于第一个问题，选择给确认增加检查和,；对于第二个问题，考虑到rdt2.0是停止等待机制，只需将增加一个1bit的序号位，并将发送、接收方一分为二，接收方检查是否为旧分组（重复分组）。

- 发送方：四个状态
	1. 等待上层调用0：若收到上层数据，则打包数据、序号0和检查和，发送，进入状态2
	2. 等待确认0：收到NAK或校验出错，则重发，状态不变；否则（收到ACK且校验正确），则进入状态3
	3. 等待上层调用1：若收到上层数据，则打包数据、序号1和检查和，发送，进入状态4
	4. 等待确认1：收到NAK或校验出错，则重发，状态不变；否则（收到ACK且校验正确），则进入状态1
- 接收方：两个状态
	1. 等待下层的0：若收到损坏分组，则发送NAK；若收到重复分组（has_seq1(rcvpkt)），则发送ACK；若收到未损坏的新分组，则递交数据，发送ACK，进入状态2
	2. 等待下层的1：若收到损坏分组，则发送NAK；若收到重复分组（has_seq0(rcvpkt)），则发送ACK；若收到未损坏的新分组，则递交数据，发送ACK，进入状态1

### rdt2.2

rdt2.2选择只使用ACK，没有NAK，取而代之的是最后一个正确收到的分组的ACK，同时带有分组序号。

- 发送方：四个状态
	1. 等待上层调用0：若收到上层数据，则打包数据、序号0和检查和，发送，进入状态2
	2. 等待确认0：收到1的ACK或校验出错，则重发，状态不变；否则（收到0的ACK且校验正确），则进入状态3
	3. 等待上层调用1：若收到上层数据，则打包数据、序号1和检查和，发送，进入状态4
	4. 等待确认1：收到0的ACK或校验出错，则重发，状态不变；否则（收到1的ACK且校验正确），则进入状态1
- 接收方：两个状态
	1. 等待下层的0：若收到损坏分组或重复分组，则发送1的ACK；若收到未损坏的新分组，则递交数据，发送0的ACK，进入状态2
	2. 等待下层的1：若收到损坏分组或重复分组，则发送0的ACK；若收到未损坏的新分组，则递交数据，发送1的ACK，进入状态1

rdt2.2的更新应该是为了统一发送方和接收方的报文格式。

### rdt3.0

第三个版本的可靠数据传输条件为：不仅信道可能出错，还有可能丢包。

解决丢包的策略为：**超时处理**。若在等待确认时超时，则重发数据。

发送方：
1. 等待上层调用0：若收到上层数据，则打包数据、序号0和检查和，发送，<font color=red>启动定时器</font>，进入状态2；如果此时收到确认，则什么都不做
2. 等待确认0：收到1的ACK或校验出错，则重发，状态不变；否则（收到0的ACK且校验正确），则进入状态3；若<font color=red>超时</font>，则重传，并重新启动计时器
3. 等待上层调用0：若收到上层数据，则打包数据、序号1和检查和，发送，<font color=red>启动定时器</font>，进入状态4；如果此时收到确认，则什么都不做
4. 等待确认0：收到0的ACK或校验出错，则重发，状态不变；否则（收到1的ACK且校验正确），则进入状态1；若<font color=red>超时</font>，则重传，并重新启动计时器

## 3.2.3 流水线技术

在rdt3.0中，发送方发送一个分组，需要等待确认。在理想情况下，发送一个分组的时间为$L/R$（传输时延），而等待确认需要一个RTT，往往RTT>>L/R，效率较低。为了解决这个问题，我们引入了流水线技术。

流水线技术的基本特性是：可以一次性发送多个分组而无需等待确认。这面临两个问题：
1. 需要确认收到的分组是哪一个，解决方法是对分组编号；
2. 需要限制发送但没收到确认的分组的个数，解决方法是滑动窗口。

### GBN（Go-Back-N）

GBN要求发送方已发送但未收到确认的分组数不超过N，即窗口大小为N。

GBN有如下特点：
- 分组首部用k-bit字段表示编号。
- 累积确认：发送方只为最早发送但未到达的分组设计时器，超时则重发窗口内所有分组。接收方发送最后一次按序到达的分组的ACK，发送方收到第n个分组的ACK后，n之前的分组自动确认。
- 发送端窗口大小$\leq 2^k-1$，接收端窗口大小为1。
- 接收方收到失序分组时，直接丢弃，发送最后一次ACK，无缓存。

发送方：（起始base=1，nextseqnum=1）只有一个状态，可以称为“等待”
- 当收到上层发送的数据，若窗口已满，则拒绝数据；否则，打包发送，若当前base与nextseqnum相等，则启动定时器。nextseqnum++。
- 收到损坏的确认，不管它（有超时操作兜底）
- 收到未损坏的确认，不用管确认序号，直接将base更改为确认号加1（累积确认规则）。如果此时base与nextseqnum相等，则停计时器，否则停计时器后启动计时器（为最早发出且未确认的分组启动定时器）
- 若超时，则重发窗口内分组，启动定时器。

接收方：（起始expectedseqnum=1，默认发送0号分组ACK），只有一个状态
- 收到未损坏的分组，且序号与expectedseqnum相等，递交数据，发送当前分组的ACK，expectedseqnum++。
- 其他情况下，直接丢失分组，发送上一次的ACK。

### 选择重传（SR）

选择重传中接收方对收到的分组进行缓存，并逐个确认，无需考虑分组是否失序。

特点：
- 发送窗口和接收窗口大小均为N。
- 发送方为每一个发送的分组设置定时器。
- 若发生超时，发送方只重传对应编号的分组。

发送方：（起始sendbase=1，nextseqnum=1）只有一个状态，可以称为“等待”
- 当收到上层发送的数据，若窗口已满，则拒绝数据或缓存；否则将数据打包发送。
- 收到损坏的确认，不管它。
- 收到未损坏的确认，如果小于sendbase，也不管它；大于sendbase，则将该分组标记为已接收；如果是sendbase，则将sendbase设置为第一个未确认的序号。
- 如果超时，重传对应该分组，重置定时器。

接收方：（起始rcvbase=1）只有一个状态
- 若收到分组序号在`[rcvbase, rcvbase+N-1]`范围内（分组正确接收），发送该序号的确认，如果没有收到过则将其缓存。如果该分组序号与rcvbase相等，则将该序号开始的连续已接收分组递交给上层。
- 若收到分组序号在`[rcvbase-N, rcvbase-1]`范围内，虽然曾经确认过，但也要发送n的确认，因为不发确认就不能向前移动。
- 其他情况则忽略该分组。

在上面的情况中，收到小于rcvbase的分组的理由：ACK可能会丢失。可能rcvbase的分组已经收到并递交，导致接收窗口移动，但发送方未收到ACK，会触发超时重传。此时发送方若不进行响应，会导致两个窗口都不移动。
